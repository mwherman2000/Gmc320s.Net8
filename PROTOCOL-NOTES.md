# Protocol notes

The library follows the command framing visible in the current PyGMC RFC1201 implementation: ASCII command bytes are sent as `<COMMAND>>`.

Examples:

- `<GETCPM>>` returns a 2-byte big-endian unsigned CPM value.
- `<GETVOLT>>` returns one byte representing tenths of a volt.
- `<GETTEMP>>` returns four bytes; the first two encode decimal temperature and byte 3 is a sign indicator in the PyGMC implementation. Confirmed working on the GMC-320S, but with two known-bad reply values - see the temperature note below.
- `<GETDATETIME>>` returns `YY MM DD HH MM SS AA`.
- `<SETDATETIME[YY][MM][DD][HH][MM][SS]>>` sets the device clock from six raw (non-ASCII) bytes and returns a single `0xAA` acknowledgement byte.
- `<GETGYRO>>` returns X/Y/Z as three big-endian signed 16-bit values followed by `AA`. Confirmed working, but it reports an **accelerometer**, not a rate gyroscope - see the note below. The API therefore exposes it as `GetOrientationAsync` returning `GmcOrientation`, named for what it measures rather than for the command.
- **The `GETCFG` calibration table is confirmed against hardware.** A real GMC-320S returned `...0064 0602 00002041 3C14 0000C842 7828 00004843...`, which decodes as three 6-byte entries starting at offset 8: a big-endian `uint16` CPM followed by a **little-endian** `float` µSv/h. That gives 1538 CPM ↔ 10.0, 15380 ↔ 100.0, and 30760 ↔ 200.0 µSv/h. Two details pin the encoding down rather than leaving it a guess: the floats are unambiguously little-endian (read big-endian they are denormal noise around 1e-41), and while both CPM endiannesses happen to be self-consistent, big-endian yields 153.8 CPM per µSv/h across all three points - exactly the 0.0065 µSv/h per CPM documented for this tube, and matching the protocol's big-endian `uint16` convention elsewhere. Little-endian would give 51.8, which would put a 19 CPM background at 0.37 µSv/h, roughly triple a plausible value. Mixed endianness inside one table is odd but it is what the device stores. `GmcCalibration` uses these points; `GetMicroSievertsPerHourAsync` is implemented on top of them rather than on a hardcoded sensitivity.
- `<GETCFG>>` returns 256 bytes. `GmcConfigParser` decodes only the leading bytes that are consistently documented across GQ RFC1201 references: byte 0 `PowerOnOff`, 1 `AlarmOnOff`, 2 `SpeakerOnOff`, 3 `GraphicModeOnOff`, 4 `BacklightTimeoutSeconds`, 5 `IdleTitleDisplayMode` - each exposed as the raw byte, without assuming a polarity for the on/off-style fields. Everything past that (notably the CPM/µSv calibration table) is firmware/model-specific and deliberately left undecoded; the full 256-byte blob is always available via `GmcConfig.Raw`. None of this is verified against physical hardware.
- `<HEARTBEAT1>>` starts a live two-byte CPS stream; the implementation uses only the low 14 bits.
- `<HEARTBEAT0>>` stops the heartbeat.
- `<GETSERIAL>>` returns 7 bytes; the device serial number is these bytes rendered as a 14-character hex string.
- `<POWEROFF>>`, `<POWERON>>` (firmware 5.71+), `<REBOOT>>`, `<FACTORYRESET>>` are fire-and-forget: the device does not send any reply.
- **Plugging in USB powers the device on, but USB does not force it to stay on.** Corrects an earlier note here that claimed the device could not be powered off at all while USB was connected - it can: the front-panel power button turns it off with the cable still attached. What USB does do is power the device on automatically when connected to a device that is off. The practical consequences for `<POWEROFF>>`/`<POWERON>>` are unchanged: neither has been observed to do anything over USB, and neither can be confirmed, since the connection carrying the command is the one the device answers on. A power cycle for testing is therefore done from the front panel (optionally with a USB unplug), not through the protocol.
- `<KEY0>>`/`<KEY1>>`/`<KEY2>>`/`<KEY3>>` simulate the four physical button presses; also fire-and-forget.
- `<SPIR[A2][A1][A0][L1][L0]>>` reads history data out of onboard flash. `A2A1A0` is a big-endian 24-bit start address; `L1L0` is a big-endian 16-bit length encoded as *(actual length - 1)*. The device replies with exactly the requested number of raw bytes. This length encoding is protocol-derived and not yet verified against physical hardware.
- Logged history entries: originally documented here as a guess ("one byte per sample, with `0xFF`-prefixed markers for special entries") before any real hardware data existed. That guess turned out wrong. A real GMC-320S read at history address 0 returned `55AA001A07150C272355AA0155AA001A`: a repeating `55 AA` sync prefix, not `0xFF`. Breaking it down: `55 AA 00` is followed by 6 bytes decoding as a YY/MM/DD/HH/MM/SS timestamp (`1A 07 15 0C 27 23` → 2026-07-21 12:39:35, the same layout `GETDATETIME`/`SETDATETIME` use), and `55 AA 01` appears to carry no payload before the next marker starts. `GmcHistoryParser.Parse` decodes marker types `0x00` and `0x01` on this basis and deliberately stops - leaving the rest as `GmcHistoryParseResult.UnparsedRemainder` - at any other marker type, since its payload length is unknown and guessing risks misreading unrelated bytes as entries. This is one observed sample, not a verified spec; other marker types almost certainly exist (notes, out-of-range values, etc.).
- Plain (non-marker) bytes, `GmcHistoryReading.Count`: originally assumed to be one-byte CPM samples. Scanning a real device's full log (~69,000 entries across ~379 repeats) showed a `55 AA 00` timestamp+marker anchor pair recurring every **exactly 182 entries**, with the real-world time between consecutive anchors consistently **179 seconds** (occasionally 178 or 180 - whole-second RTC rounding jitter, not real drift). 182 entries = 1 timestamp + 1 marker + 180 plain readings, and 180 readings in ~179 seconds is ~1 reading/second - far more consistent with a per-second CPS value than a per-minute CPM value (a true 60-second rolling CPM wouldn't fluctuate sample-to-sample the way these values do; their magnitude and volatility instead matches the live `HEARTBEAT1` CPS stream from the same device). This is why the field is named `Count`, not `Cpm` - the interpretation is a strong inference from timing and magnitude, not a documented fact.
- `FindHistoryEndAsync` is a heuristic, not a documented protocol fact: it treats a sufficiently long run of `0xFF` bytes as "erased flash past the end of logged data." The one real sample above contains no `0xFF` at all in either the markers or (per the above) single-byte samples below 255, which supports `0xFF` as a reasonable erased-flash signal here - though a real reading of exactly 255 would also produce a `0xFF` byte, so `minErasedRunLength` (default 64) exists to make a long coincidental run implausible rather than to rule it out entirely. The default 1MB (`0x100000`) upper bound is the commonly cited GMC-320 flash size, also unverified. Against real hardware this returned addresses in the `0x01A3xx`-`0x01ACxx` range (~107-110K) across several runs, well before the scan bound.
- **Unknown: what happens when the log buffer fills up.** Nothing in the (reverse-engineered) RFC1201 spec documents circular-buffer/wraparound behavior, and no real device tested here has ever come close to filling its buffer (~110K/1MB observed, if 1MB is even the right size). Plausible untested behaviors: logging stops until the user erases history via the device menu or GQ's PC software; the buffer wraps and silently overwrites the oldest entries; or something else entirely. `FindHistoryEndAsync` assumes an erased-flash gap exists to find - a full, wrapped buffer would look like continuous data everywhere and this probe would hit `maxAddress` and return `null` without any indication of *why*. At the ~1 reading/second rate observed above, filling a 1MB buffer would take roughly 12 days of continuous logging - a real way to eventually settle this empirically, just not a fast one.
- **The ~1 reading/second rate is now confirmed exactly, not just inferred.** A factory reset wiped the log, and reading the fresh one from address 0 gave an unambiguous measurement that the ~110K-entry log could not: `55AA00 1A090E0B321D 55AA01` (11:50:29), immediately followed by a second identical anchor pair at the same second, then **12** plain readings, then `55AA00 1A090E0B3229 55AA01` (11:50:41). Twelve readings between timestamps exactly twelve seconds apart is **1.00 reading/second**, which promotes the `Count`-not-`Cpm` naming from a strong inference to a measured fact about the logging rate. Independently, the write pointer grew 603 → 1407 bytes over 726 seconds (~1.04 readings/second once anchor overhead is subtracted).
- **A restart writes a doubled anchor pair, and resets the cadence.** Confirmed deliberately: four power cycles (front-panel off, then USB replug to power on) at roughly 3, 2 and 1 minute intervals produced exactly four *doubled* anchors - two `timestamp+marker` sets back to back with **zero readings between them** but a real gap in their timestamps. Those gaps were 89s, 17s, 13s and 21s, matching the roughly 10-20 seconds the device spent switched off, so the pair brackets the outage: the log simply stops and resumes, with the missing time visible only as the jump between the two timestamps. It is the same shape the log shows at address 0 after a factory reset, where the two timestamps were identical. The periodic rhythm does not survive: the last undisturbed interval before the experiment was a textbook 182 entries / 179 seconds, and nothing afterwards resembled it (gaps of 133, 89, 118, 17, 84, 13, 42 and 21 seconds). Batch lengths across the run ranged from **2 to 106 entries**.
  - Caveat: a power-on anchor is byte-identical to a periodic one, so a log alone cannot distinguish "the device restarted" from "a short session ended" except by the spacing. A doubled pair with a time gap is the only reliable restart signature found so far.
  - Caveat: the reading counts in that region do not reconcile with elapsed time in either direction - see BACKLOG.md. Do not interpolate a wall-clock time for an individual reading by counting forward from an anchor until that is understood.
- **Batch length between anchors is emphatically not a constant.** The same fresh log opens with a **zero**-reading batch (two anchor pairs at the identical timestamp, back to back) followed by a **12**-reading batch - against the ~180 seen between undisturbed natural anchors. Earlier logs showed a 141-reading batch and further zero-reading runs around power-on events. Anything that derives entry positions or byte offsets from an assumed batch length will mis-parse real logs; `GmcHistoryParser` and `Gmc320sClient.GetRecentHistoryAsync` deliberately assume nothing about it.
- **A device-menu factory reset erases the history log.** The protocol itself has no history-erase command (`ECFG` only erases configuration), but resetting from the device's own menu restarts the log at address 0 - observed directly: a write pointer of `0x01ACAA` (~109,738) became `0x0001F9` (505) with a fresh first timestamp. The same reset also returned the leading `GETCFG` bytes to defaults (`PowerOnOff` 255 → 0, `SpeakerOnOff` 0 → 1), which incidentally confirms those bytes carry real device state rather than the garbage their odd values had suggested - though their exact offsets and meanings remain unverified.
- **`GETTEMP` and `GETGYRO` do work on the GMC-320S - an earlier note here claiming otherwise was wrong.** The suspicion was that this model lacked the hardware and returned junk, based on repeated 85.0 °C temperatures (85 = `0x55`) and gyro values on suspiciously round numbers. Dumping the raw replies via `SendRawAsync` disproved it outright: `<GETTEMP>>` → `16 00 00 AA` (22, 0 tenths, positive sign, `0xAA` terminator = 22.0 °C) and `<GETGYRO>>` → `0010 0030 C090 AA` (X=16, Y=48, Z=-16240, `0xAA` terminator). Both are well-formed and correctly decoded. The lesson is that the decoded *values* looked wrong while the *bytes* were fine, so the two real explanations are:
  - **The temperature encoding is plain binary, and the existing decode is correct.** Readings sat ~5.7 °C above a known 17 °C room temperature, which raised the possibility that the whole-degrees byte was BCD (`0x16` → 16 rather than 22) - under BCD the observed samples became 16.0/16.7/17.3, a much tighter fit to ambient. Warming the device by hand settled it: consecutive reads gave `19 08` → `19 09` → `1A 00`, i.e. 25.8 → 25.9 → **26.0 °C**. The nibble `A` in `0x1A` is not a valid BCD digit, and the roll from `0x19` to `0x1A` is plain binary increment, so BCD is disproven. The offset from ambient is real self-heating inside a USB-powered enclosure (hand-warming added a further ~4 °C, tracked smoothly).
  - **`GETTEMP` is stable across consecutive reads; a "first read is stale" theory was tested and rejected.** Twenty back-to-back raw reads returned byte-identical `1B 06 00 AA` (27.6 °C). What had looked like a stale first read was really thermal lag: across three runs the gap between the first reading of a session and a burst moments later was 0 °C while the device was thermally settled, 3.8 °C while it was being hand-warmed, and 1.6 °C while it was re-equilibrating afterwards. The reading tracks the sensor, which lags the environment - re-reading cannot fix that and a blanket double-read buys nothing.
  - **Two known-bad replies exist, and both are now rejected rather than returned.** The first was captured raw: `00 00 01 AA`, the sign flag set over a zero magnitude - "-0.0 °C" - which appeared roughly once in thirty reads with the following read correct. It is recognised *structurally*, which is the precise way to do it. The second is the recurring **85.0 °C**, the classic power-on-reset default of common digital temperature sensors and far outside this device's specified 0-50 °C ambient range; it has never been captured raw, so it is caught by a plausibility range (-20 to 70 °C, deliberately far wider than any genuine reading including the 5-6 °C self-heating offset) rather than by a value comparison. `GetTemperatureCelsiusAsync` re-reads up to three times and throws `InvalidDataException` if every attempt is implausible, so a caller never silently receives a wrong number. Retrying is non-destructive - a genuine reading simply passes on the first attempt - which is what makes guarding safe despite the 85.0 encoding being unconfirmed. If an 85.0 event is ever captured raw and turns out to have a structural signature like the negative-zero case, the range check should be replaced by that.
  - **`GETGYRO` reports an accelerometer, not a rate gyroscope, at 12-bit resolution scaled 16384 counts per g.** Six stationary samples pin this down exactly. Every component of every sample is a multiple of 16, so the low four bits are always zero: the sensor is **12-bit, left-shifted into a 16-bit field**, giving 4096 effective steps rather than 65536. Dividing the raw values by 16 puts Z on -1024 = -2^10, i.e. **1024 counts per g after the shift, 16384 before it** - a 12-bit part at ±2 g full scale, a very common configuration. The decisive check is the vector magnitude: across all six samples `sqrt(X² + Y² + Z²)` came to 0.991-1.020 g, i.e. 1.000 g within noise. A stationary accelerometer *must* read exactly 1 g because gravity never switches off, whereas a stationary rate gyroscope would read zero on all three axes. So the values are the static gravity vector, and on a flat device X and Y of 1-18 counts (of 1024) correspond to under ~1° of tilt. Stood on edge, Z should collapse toward zero and whichever axis is then vertical should swing to about ±16384. Raw samples, X/Y/Z before the shift: `(192, 64, -16576)`, `(176, 224, -16384)`, `(16, -176, -16704)`, `(288, 48, -16288)`, `(272, 32, -16352)`, `(16, 48, -16240)`.
  - **Confirmed out-of-sample by re-orienting the device.** The 16384-per-g figure was derived entirely from flat readings, then correctly predicted what standing the device on edge would do: Z collapsed from -0.994 g to 0.071 g while Y rose to 0.956 g, and every value stayed a multiple of 16. The tilt implied by that reading, `atan(sqrt(256² + 1168²) / 15664)` = **4.4° off vertical**, matched the roughly 5° the device was visibly leaning - a physically correct angle recovered from an orientation the scale factor was never fitted to.
  - **Full six-position calibration: 16384 counts per g is accurate only for Z, and the other two axes fail in opposite ways.** Gravity's magnitude must read 1.000 g at any orientation, so pointing each axis up and then down in turn - the standard six-position routine - measures that axis's response to +1 g and -1 g. From those two, gain and offset separate as `k = (r₊ - r₋) / 2` and `b = (r₊ + r₋) / 2`:

    | Axis | +1 g reads | -1 g reads | Gain | Offset | Dominated by |
    |---|---|---|---|---|---|
    | X | +1.006 g | -0.983 g | **0.995** (0.6% low) | **+0.011 g** | bias |
    | Y | +0.956 g | -0.962 g | **0.960** (4.0% low) | **-0.002 g** | gain |
    | Z | +0.996 g | -1.002 g | **0.999** (0.1% low) | **-0.003 g** | neither; well trimmed |

    Measuring only one direction per axis is actively misleading, and an earlier version of this note fell into exactly that trap: X was recorded as "1.7% low", implying a gain error, when in fact its gain is nearly perfect and the discrepancy is almost entirely a +0.011 g bias that happened to subtract in the one direction tested. Y is the mirror image - negligible bias, but a genuine 4.2% gain shortfall. With a single direction the two are mathematically inseparable, which is the whole reason the six-position routine exists.

    Practical upshot: the shared 16384 scale is fine for coarse "which way is up" work, which is presumably all the device itself needs it for. For anything quantitative, apply per-axis gain and offset. Note also that readings taken while the device is still being handled are unusable - one Y-down sample set drifted 0.14 g on Z between consecutive reads, a spread as large as the effect being measured, so let the device settle before trusting a reading.

    Raw samples remain multiples of 16 in all six orientations, e.g. X-down `(-16048, -32, -224)`, X-up `(16480, -240, -304)`, Z-up `(224, -128, 16288)`.
  - **Beyond ±2 g the value WRAPS rather than clipping - a reading can come back sign-inverted and entirely plausible-looking.** This corrects an earlier note here that called it clipping. Across two shake captures, apparent single-sample jumps of 3.4-3.8 g appeared, always with one axis at a rail while the other two moved by a sane ~0.2-0.4 g. Reading them as two's-complement overflow of the 12-bit value (rails at +2047/-2048 LSB) resolves every one of them to a plausible change. Worked example, X between two consecutive samples: `+26640` → `-30592` is nominally -3.49 g, but as a wrap it is 1665 → 2047 (+382 LSB), over to -2048 (+1), then up to -1912 (+136) = **+519 LSB = +0.51 g**, matching the +0.41 g that Y moved in the same interval. The decisive evidence is that **the rail value itself is never observed**: a clipping sensor pins at exactly -32768 and plateaus there, whereas across ~300 samples the nearest reading was -32592 before the sign flipped. Clipping plateaus; wrapping passes through.
    - Consequence: overflow is undetectable from a single sample, and worse than clipping would be, since the value is not merely capped but wrong in sign. Sustained acceleration above 2 g - a bicycle wheel at road speed reaches roughly 6 g at the rim - produces readings that look valid and are not. If in doubt, sample continuously and treat any implausibly large step between consecutive samples as a suspected wrap.
  - **Polling is fast enough for hand motion; an earlier claim of aliasing here was wrong.** Those 3.4 g jumps were attributed to undersampling before the wrap explanation was found. Measured properly, the shake in that capture had a period of about 28 samples, roughly 1.7 Hz, against a sample rate of 47 Hz - oversampled by around 14x, nowhere near the Nyquist limit. Read rate itself measures **47-65 Hz (15-21 ms per read)** and varies with host load; see the sampling-rate note below for why it is transport-bound.
  - **Command latency is device-bound, not transport-bound. Each command costs what the firmware has to do.** An earlier version of this note claimed the opposite - that over 90% of a read was CH340 latency and the driver was the lever. That was inferred from timing a single command, which cannot distinguish the two causes. Timing six commands of differing reply sizes settles it (`--benchmark`, minimum of 12 calls each; wire time is the request plus reply at 115200 8N1, 10 bits per byte):

    | Command | Reply | min ms | wire ms | **overhead ms** | slow calls |
    |---|---|---|---|---|---|
    | `GETVER` | 14 | 6.08 | 2.00 | **4.08** | 0 |
    | `GETCFG` | 256 | 29.52 | 23.00 | **6.52** | 0 |
    | `GETGYRO` | 7 | 12.07 | 1.48 | **10.60** | 0 |
    | `GETVOLT` | 1 | 14.59 | 0.95 | **13.63** | 0 |
    | `GETTEMP` | 4 | 166.89 | 1.22 | **165.68** | 12 |
    | `GETCPM` | 2 | 3.02 | 0.95 | 2.07 | **11** |

    The overhead does not scale with reply size; it varies by *command*. `GETVER` returns 14 bytes in 6 ms while `GETGYRO` returns half as many in 12 ms. **The USB driver cannot tell which command it is carrying, so a per-command difference cannot be transport latency** - it has to be the firmware. Reading the table that way:
    - **The USB round trip is only about 4 ms**, taken from `GETVER`, which just returns a constant string and so represents the least work the firmware can do.
    - Everything above that is the device working: roughly 6.6 ms for `GETGYRO` to read the accelerometer over I2C, 9.6 ms for `GETVOLT`'s ADC conversion, 2.5 ms for `GETCFG`'s flash read.
    - So the orientation polling ceiling is about **83 Hz** (12.07 ms), set by the device. Even a perfect transport would only recover the ~4 ms, reaching perhaps 125 Hz. The loop rate observed in practice, 47-65 Hz, is lower again because of console output per sample.
    - Report the **minimum**, never the mean. A single retried call costs seconds and swamps an average, so a mean over these measures the retry policy rather than the transport - the first version of this benchmark reported 4627 ms for `GETCPM` for exactly that reason.

    Two candidate transport fixes were tried before the above was understood. Both failed, and are recorded so the work is not repeated:
    - **The driver exposes no usable latency control.** Unlike FTDI parts there is no latency timer. Windows' generic port dialog offers a "Receive Buffer" (FIFO trigger) slider, but the setting will not stick: after changing it the device's `Device Parameters` key contains `TxFIFO` and `ForceFifoEnable` but **no `RxFIFO` value at all**, so the CH341SER driver simply discards it. The `PollingPeriod` value in the same key is WCH-specific and sits at its `0` default; its semantics are undocumented and it has not been tested. Given the finding above, none of this would have bought more than ~4 ms anyway.
    - **It is not this library's doing.** `Command` issues a `DiscardInBuffer` purge before every write, a plausible extra driver round trip. Removing it measured 15.7 ms/read against a 15.4 ms baseline - no effect - so the purge was kept for its desync-recovery value.

    The protocol is strictly request/response with no message IDs, so reads cannot be pipelined regardless.
  - **`GETTEMP` blocks for ~170 ms while the sensor converts.** Twelve consecutive calls all took 167-184 ms, tightly clustered - a real cost, not retries. That is a characteristic digital-temperature-sensor conversion time, and it retroactively explains the not-ready values documented above: the sensor genuinely needs that long to produce a figure, so anything polling faster than about 6 Hz gets a stale or not-ready answer rather than a fresh one.
  - **`GETCPM` cannot be polled in a tight loop: a request arriving too soon after the previous one is silently ignored.** Benchmarked in isolation, 20 consecutive calls each cost about 5.1 seconds - a full read timeout on the first attempt, then success roughly 100 ms later on the retry. Raising the read timeout from 5 s to 30 s made each call cost about 30 s instead, so **the first attempt never receives a reply no matter how long it waits**. That rules out slowness: the device is discarding the request rather than answering late. The only thing the successful retry has that the failed attempt lacks is the 100 ms gap preceding it.
    - An earlier version of this note called it an off-by-one desync, on the strength of one 3.02 ms call among the timeouts. The 30-second test disproved that; a desynced reply would still have arrived.
    - `GETGYRO` and `GETVER` are unaffected at 12 ms and 6 ms intervals, so it is specific to `GETCPM`, plausibly because the firmware recomputes CPM on a roughly one-second cadence and ignores requests between updates.
    - Practical consequence: a caller polling CPM in a loop pays a full read timeout per reading and will not notice, because the retry hides it. Pace CPM reads about a second apart. This also explains an apparently healthy six-call test earlier - CPM climbed from 14 to 21 across it, meaning some 30 seconds had elapsed for six reads, i.e. every one had quietly cost 5 s.
  - **`IsStable` on a single sample has a measured ~10% false-positive rate under motion.** In that same 100-sample capture, 10 samples sat within the stability tolerance because the acceleration vector happened to be sweeping through 1 g magnitude at that instant. `Gmc320sClient.GetStableOrientationAsync` exists for this: given the same data it correctly refused to return anything, throwing rather than surfacing one of the ten plausible-looking samples.
- **The 182-entry/179s cadence holds over the long run, not just a short window.** Re-scanning the same real device roughly two days later (log end grown from ~110K to ~104,700+ entries) found the pattern unbroken the entire way: every recurring timestamp was still exactly 182 entries and ~179 seconds after the last, all the way up through entries logged just seconds before the scan itself ran (the final timestamp found was within ~1 minute of the host machine's current time). That means the device logged continuously, without gaps, for the full ~2-day span between the two scans - a good real-world sanity check that both the `Count`-not-`Cpm` inference and `FindHistoryEndAsync`'s reported end address are tracking genuine, live, uninterrupted logging rather than some artifact of how the log happened to look at one point in time.

These details should be treated as protocol-derived implementation facts, while exact behavior on a particular GMC-320S firmware should be validated against physical hardware.
