# Protocol notes

The library follows the command framing visible in the current PyGMC RFC1201 implementation: ASCII command bytes are sent as `<COMMAND>>`.

Examples:

- `<GETCPM>>` returns a 2-byte big-endian unsigned CPM value.
- `<GETVOLT>>` returns one byte representing tenths of a volt.
- `<GETTEMP>>` returns four bytes; the first two encode decimal temperature and byte 3 is a sign indicator in the PyGMC implementation. **Suspect on the GMC-320S** - see the temperature/gyro note below.
- `<GETDATETIME>>` returns `YY MM DD HH MM SS AA`.
- `<SETDATETIME[YY][MM][DD][HH][MM][SS]>>` sets the device clock from six raw (non-ASCII) bytes and returns a single `0xAA` acknowledgement byte.
- `<GETGYRO>>` returns X/Y/Z as three big-endian signed 16-bit values followed by `AA`. **Suspect on the GMC-320S** - see the temperature/gyro note below.
- **The `GETCFG` calibration table is confirmed against hardware.** A real GMC-320S returned `...0064 0602 00002041 3C14 0000C842 7828 00004843...`, which decodes as three 6-byte entries starting at offset 8: a big-endian `uint16` CPM followed by a **little-endian** `float` µSv/h. That gives 1538 CPM ↔ 10.0, 15380 ↔ 100.0, and 30760 ↔ 200.0 µSv/h. Two details pin the encoding down rather than leaving it a guess: the floats are unambiguously little-endian (read big-endian they are denormal noise around 1e-41), and while both CPM endiannesses happen to be self-consistent, big-endian yields 153.8 CPM per µSv/h across all three points - exactly the 0.0065 µSv/h per CPM documented for this tube, and matching the protocol's big-endian `uint16` convention elsewhere. Little-endian would give 51.8, which would put a 19 CPM background at 0.37 µSv/h, roughly triple a plausible value. Mixed endianness inside one table is odd but it is what the device stores. `GmcCalibration` uses these points; `GetMicroSievertsPerHourAsync` is implemented on top of them rather than on a hardcoded sensitivity.
- `<GETCFG>>` returns 256 bytes. `GmcConfigParser` decodes only the leading bytes that are consistently documented across GQ RFC1201 references: byte 0 `PowerOnOff`, 1 `AlarmOnOff`, 2 `SpeakerOnOff`, 3 `GraphicModeOnOff`, 4 `BacklightTimeoutSeconds`, 5 `IdleTitleDisplayMode` - each exposed as the raw byte, without assuming a polarity for the on/off-style fields. Everything past that (notably the CPM/µSv calibration table) is firmware/model-specific and deliberately left undecoded; the full 256-byte blob is always available via `GmcConfig.Raw`. None of this is verified against physical hardware.
- `<HEARTBEAT1>>` starts a live two-byte CPS stream; the implementation uses only the low 14 bits.
- `<HEARTBEAT0>>` stops the heartbeat.
- `<GETSERIAL>>` returns 7 bytes; the device serial number is these bytes rendered as a 14-character hex string.
- `<POWEROFF>>`, `<POWERON>>` (firmware 5.71+), `<REBOOT>>`, `<FACTORYRESET>>` are fire-and-forget: the device does not send any reply.
- **USB power overrides the power commands.** Observed on real hardware: the device cannot be powered off at all while USB is connected (bus power keeps it running), and plugging the cable in powers it on. So `<POWEROFF>>` has no visible effect over a USB connection, `<POWERON>>` is moot (the device is necessarily already on by the time a connection exists to send it), and neither can be confirmed, since the connection that carries the command is the same one that keeps the device awake. A consequence for testing: a genuine power cycle means unplugging and replugging USB - which also drops the serial connection - rather than anything the protocol can do.
- `<KEY0>>`/`<KEY1>>`/`<KEY2>>`/`<KEY3>>` simulate the four physical button presses; also fire-and-forget.
- `<SPIR[A2][A1][A0][L1][L0]>>` reads history data out of onboard flash. `A2A1A0` is a big-endian 24-bit start address; `L1L0` is a big-endian 16-bit length encoded as *(actual length - 1)*. The device replies with exactly the requested number of raw bytes. This length encoding is protocol-derived and not yet verified against physical hardware.
- Logged history entries: originally documented here as a guess ("one byte per sample, with `0xFF`-prefixed markers for special entries") before any real hardware data existed. That guess turned out wrong. A real GMC-320S read at history address 0 returned `55AA001A07150C272355AA0155AA001A`: a repeating `55 AA` sync prefix, not `0xFF`. Breaking it down: `55 AA 00` is followed by 6 bytes decoding as a YY/MM/DD/HH/MM/SS timestamp (`1A 07 15 0C 27 23` → 2026-07-21 12:39:35, the same layout `GETDATETIME`/`SETDATETIME` use), and `55 AA 01` appears to carry no payload before the next marker starts. `GmcHistoryParser.Parse` decodes marker types `0x00` and `0x01` on this basis and deliberately stops - leaving the rest as `GmcHistoryParseResult.UnparsedRemainder` - at any other marker type, since its payload length is unknown and guessing risks misreading unrelated bytes as entries. This is one observed sample, not a verified spec; other marker types almost certainly exist (notes, out-of-range values, etc.).
- Plain (non-marker) bytes, `GmcHistoryReading.Count`: originally assumed to be one-byte CPM samples. Scanning a real device's full log (~69,000 entries across ~379 repeats) showed a `55 AA 00` timestamp+marker anchor pair recurring every **exactly 182 entries**, with the real-world time between consecutive anchors consistently **179 seconds** (occasionally 178 or 180 - whole-second RTC rounding jitter, not real drift). 182 entries = 1 timestamp + 1 marker + 180 plain readings, and 180 readings in ~179 seconds is ~1 reading/second - far more consistent with a per-second CPS value than a per-minute CPM value (a true 60-second rolling CPM wouldn't fluctuate sample-to-sample the way these values do; their magnitude and volatility instead matches the live `HEARTBEAT1` CPS stream from the same device). This is why the field is named `Count`, not `Cpm` - the interpretation is a strong inference from timing and magnitude, not a documented fact.
- `FindHistoryEndAsync` is a heuristic, not a documented protocol fact: it treats a sufficiently long run of `0xFF` bytes as "erased flash past the end of logged data." The one real sample above contains no `0xFF` at all in either the markers or (per the above) single-byte samples below 255, which supports `0xFF` as a reasonable erased-flash signal here - though a real reading of exactly 255 would also produce a `0xFF` byte, so `minErasedRunLength` (default 64) exists to make a long coincidental run implausible rather than to rule it out entirely. The default 1MB (`0x100000`) upper bound is the commonly cited GMC-320 flash size, also unverified. Against real hardware this returned addresses in the `0x01A3xx`-`0x01ACxx` range (~107-110K) across several runs, well before the scan bound.
- **Unknown: what happens when the log buffer fills up.** Nothing in the (reverse-engineered) RFC1201 spec documents circular-buffer/wraparound behavior, and no real device tested here has ever come close to filling its buffer (~110K/1MB observed, if 1MB is even the right size). Plausible untested behaviors: logging stops until the user erases history via the device menu or GQ's PC software; the buffer wraps and silently overwrites the oldest entries; or something else entirely. `FindHistoryEndAsync` assumes an erased-flash gap exists to find - a full, wrapped buffer would look like continuous data everywhere and this probe would hit `maxAddress` and return `null` without any indication of *why*. At the ~1 reading/second rate observed above, filling a 1MB buffer would take roughly 12 days of continuous logging - a real way to eventually settle this empirically, just not a fast one.
- **The ~1 reading/second rate is now confirmed exactly, not just inferred.** A factory reset wiped the log, and reading the fresh one from address 0 gave an unambiguous measurement that the ~110K-entry log could not: `55AA00 1A090E0B321D 55AA01` (11:50:29), immediately followed by a second identical anchor pair at the same second, then **12** plain readings, then `55AA00 1A090E0B3229 55AA01` (11:50:41). Twelve readings between timestamps exactly twelve seconds apart is **1.00 reading/second**, which promotes the `Count`-not-`Cpm` naming from a strong inference to a measured fact about the logging rate. Independently, the write pointer grew 603 → 1407 bytes over 726 seconds (~1.04 readings/second once anchor overhead is subtracted).
- **Batch length between anchors is emphatically not a constant.** The same fresh log opens with a **zero**-reading batch (two anchor pairs at the identical timestamp, back to back) followed by a **12**-reading batch - against the ~180 seen between undisturbed natural anchors. Earlier logs showed a 141-reading batch and further zero-reading runs around power-on events. Anything that derives entry positions or byte offsets from an assumed batch length will mis-parse real logs; `GmcHistoryParser` and `Gmc320sClient.GetRecentHistoryAsync` deliberately assume nothing about it.
- **A device-menu factory reset erases the history log.** The protocol itself has no history-erase command (`ECFG` only erases configuration), but resetting from the device's own menu restarts the log at address 0 - observed directly: a write pointer of `0x01ACAA` (~109,738) became `0x0001F9` (505) with a fresh first timestamp. The same reset also returned the leading `GETCFG` bytes to defaults (`PowerOnOff` 255 → 0, `SpeakerOnOff` 0 → 1), which incidentally confirms those bytes carry real device state rather than the garbage their odd values had suggested - though their exact offsets and meanings remain unverified.
- **`GETTEMP` and `GETGYRO` do work on the GMC-320S - an earlier note here claiming otherwise was wrong.** The suspicion was that this model lacked the hardware and returned junk, based on repeated 85.0 °C temperatures (85 = `0x55`) and gyro values on suspiciously round numbers. Dumping the raw replies via `SendRawAsync` disproved it outright: `<GETTEMP>>` → `16 00 00 AA` (22, 0 tenths, positive sign, `0xAA` terminator = 22.0 °C) and `<GETGYRO>>` → `0010 0030 C090 AA` (X=16, Y=48, Z=-16240, `0xAA` terminator). Both are well-formed and correctly decoded. The lesson is that the decoded *values* looked wrong while the *bytes* were fine, so the two real explanations are:
  - **The temperature encoding is plain binary, and the existing decode is correct.** Readings sat ~5.7 °C above a known 17 °C room temperature, which raised the possibility that the whole-degrees byte was BCD (`0x16` → 16 rather than 22) - under BCD the observed samples became 16.0/16.7/17.3, a much tighter fit to ambient. Warming the device by hand settled it: consecutive reads gave `19 08` → `19 09` → `1A 00`, i.e. 25.8 → 25.9 → **26.0 °C**. The nibble `A` in `0x1A` is not a valid BCD digit, and the roll from `0x19` to `0x1A` is plain binary increment, so BCD is disproven. The offset from ambient is real self-heating inside a USB-powered enclosure (hand-warming added a further ~4 °C, tracked smoothly).
  - **`GETTEMP` is stable across consecutive reads; a "first read is stale" theory was tested and rejected.** Twenty back-to-back raw reads returned byte-identical `1B 06 00 AA` (27.6 °C). What had looked like a stale first read was really thermal lag: across three runs the gap between the first reading of a session and a burst moments later was 0 °C while the device was thermally settled, 3.8 °C while it was being hand-warmed, and 1.6 °C while it was re-equilibrating afterwards. The reading tracks the sensor, which lags the environment - re-reading cannot fix that and a blanket double-read buys nothing.
  - **There is one genuine defect: an occasional impossible "negative zero" reply.** `00 00 01 AA` - the sign flag set over a zero magnitude - appeared roughly once in thirty reads, with the immediately following read correct. `GetTemperatureCelsiusAsync` therefore rejects exactly that pattern and re-reads once, rather than double-reading unconditionally. The recurring **85.0 °C** readings may be a further not-ready value (85 °C is the classic power-on-reset default of common digital temperature sensors), but no raw capture of an 85.0 event exists yet and 85.0 is a representable temperature, so it is deliberately *not* filtered - that would be guessing.
  - **`GETGYRO` reports an accelerometer, not a rate gyroscope.** On a device lying flat, Z sits near -16384 with X and Y near zero - that is -1g on Z at roughly 16384 counts per g, i.e. gravity. The "suspiciously round" Z was the correct answer all along.
- **The 182-entry/179s cadence holds over the long run, not just a short window.** Re-scanning the same real device roughly two days later (log end grown from ~110K to ~104,700+ entries) found the pattern unbroken the entire way: every recurring timestamp was still exactly 182 entries and ~179 seconds after the last, all the way up through entries logged just seconds before the scan itself ran (the final timestamp found was within ~1 minute of the host machine's current time). That means the device logged continuously, without gaps, for the full ~2-day span between the two scans - a good real-world sanity check that both the `Count`-not-`Cpm` inference and `FindHistoryEndAsync`'s reported end address are tracking genuine, live, uninterrupted logging rather than some artifact of how the log happened to look at one point in time.

These details should be treated as protocol-derived implementation facts, while exact behavior on a particular GMC-320S firmware should be validated against physical hardware.
